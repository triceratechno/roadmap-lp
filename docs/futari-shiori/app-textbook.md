# ふたりのアプリをつくるための教科書

自分のアプリだけを題材にした、アプリ開発の入門書。

---

## この本について

この本のゴールは、コードを自分で書けるようになることではありません。
**Claude Code に的確に指示を出し、返ってきたものを判断できるようになること**です。

そのために必要なのは、細かい文法ではなく地図です。
どこに何があって、何がどう繋がっていて、どこを触ると何が変わるのか。
それが頭に入っていれば、指示は自然と具体的になります。

例として使うのは、いま作っている旅行しおりアプリだけです。
架空のToDoアプリは一度も出てきません。

読む順番は上からで構いませんが、第6章と第10章がこの本の中心です。
時間がないときはその2つだけでも効きます。

---

# 第1章 アプリは何でできているか

## 3つの部品しかない

どんなアプリも、突き詰めると3つの部品でできています。

**画面** ユーザーが見て触る部分
**データ** 表示される中身
**置き場所** そのデータがどこに保管されているか

あなたのアプリで言えば、こうなります。

- 画面 = タイムライン、日付チップ、持ち物のチェックリスト
- データ = 9月18日20:25 神戸発、という予定そのもの
- 置き場所 = リポジトリの中のJSONファイル、あるいはサーバーのデータベース

開発中に起きる問題のほとんどは、この3つのどれかに分類できます。
「表示が崩れた」は画面の問題、「値が古い」はデータの問題、「彼女の端末に反映されない」は置き場所の問題です。

Claude Code に相談するとき、まずこの3つのどれの話をしているのかをはっきりさせるだけで、伝わり方がかなり変わります。

## なぜ App Store に出さないのか

スマホアプリと聞くと、App Store や Google Play に並ぶものを想像すると思います。
あれは**ネイティブアプリ**と呼ばれ、iPhone用とAndroid用を別々の言語で作り、審査を通し、更新のたびにまた審査を受けます。2人で使うアプリには重すぎます。

あなたが作るのは**ウェブアプリ**です。
ブラウザで開くもので、URLさえ知っていれば誰でも見られます。審査はなく、更新は即座に反映されます。

そして後の章で説明する PWA という仕組みを足すと、ホーム画面にアイコンを置けて、開いたときにブラウザのアドレスバーが消えます。
見た目も操作感もふつうのアプリになります。ストアに出す必要がありません。

## あなたのアプリの全体図

```
   彼女のiPhone            あなたのiPhone
        │                      │
        └──────────┬───────────┘
                   │  URLを開く
                   ▼
        ┌──────────────────────┐
        │  Cloudflare Pages    │  ← 画面のファイルが置いてある
        │  （公開されている）   │     旅程JSONもここに含まれる
        └──────────┬───────────┘
                   │  メモの読み書きだけ
                   ▼
        ┌──────────────────────┐
        │  Pages Functions     │  ← 受付窓口
        │        ↓             │
        │  D1（データベース）   │  ← 書き込まれたメモが貯まる
        └──────────────────────┘
```

この図が頭に入っていれば、この本の半分は終わりです。

# 第2章 ブラウザは何をしているのか

## 3つの言語の役割分担

ブラウザは3種類のファイルを受け取って、画面を組み立てます。

**HTML** 構造。「ここに見出し、ここに文章、ここにボタン」
**CSS** 見た目。「見出しは濃紺で24px、ボタンは角丸」
**JavaScript** 動き。「ボタンが押されたら中身を書き換える」

DTMで例えるなら、HTMLがトラック構成、CSSがミックス、JavaScriptがオートメーションです。
トラックがなければ何も鳴らず、ミックスがなければ聴けたものではなく、オートメーションがなければ最初から最後まで同じことしか起きません。

あなたのアプリで言えば、タイムラインの各予定が並んでいるのがHTML、時刻が等幅で濃紺なのがCSS、現在時刻のラインが下に動いていくのがJavaScriptです。

## ページを開くとは

URLを開くと、ブラウザはサーバーにファイルを要求します。
サーバーがHTMLを返し、ブラウザがそれを読んで「CSSとJavaScriptも必要だ」と気づき、追加で要求します。全部揃ったところで画面を組み立てて表示します。

だから通信が遅いと表示も遅い。
だからオフラインだと開けない。第9章で、それを開けるようにする方法を説明します。

# 第3章 Reactが解決している問題

## 素のJavaScriptだと何が起きるか

「日付チップをタップしたら、その日のタイムラインに切り替える」を素のJavaScriptで書くとします。

やることはこうなります。今表示されているタイムラインを消す。新しい日のデータを取ってくる。予定の数だけ要素を作る。それを画面に差し込む。ついでに日付チップの選択状態も切り替える。現在時刻ラインを出すか消すかも判断する。

**画面のどこを、どう書き換えるか**を、全部手で書くわけです。
予定が増えたり、条件が増えたりするたびに、この手順が複雑になっていきます。バグの温床です。

## Reactの発想

Reactはこれを逆転させます。

書き換え手順を書くのをやめて、**「データがこうなっているとき、画面はこう見える」**とだけ書きます。
データが変わったら、Reactが差分を計算して、変わったところだけ勝手に書き換えます。

選択中の日付が19日なら19日のタイムラインが見える。20日に変わったら20日のが見える。
その「変わったときにどう書き換えるか」は書かなくていい。

これがReactを使う理由の全てです。

## 覚えるのは3つだけ

### コンポーネント

画面の部品です。関数として書かれ、何を表示するかを返します。

あなたのアプリなら、こう分かれるはずです。

- `DayChips` 上部の日付チップの列
- `Timeline` 選択された日のタイムライン全体
- `TimelineItem` 予定1件
- `NowLine` 現在時刻の横線
- `PackingSection` 持ち物のセクション

部品を組み合わせて画面を作ります。DAWのトラックに近い考え方です。
1つのトラックに全部の音を突っ込まず、役割ごとに分けるのと同じ理由で分けます。

### props

親のコンポーネントから子に渡す値です。上から下へ、一方通行で流れます。

`Timeline` が `TimelineItem` に「この予定を表示して」と予定データを渡す。
これがpropsです。子は受け取った値を表示するだけで、自分で書き換えることはしません。

信号の流れと同じで、上流から下流へ流れます。逆流はしません。

### state

時間とともに変わる値です。これが変わると画面が描き直されます。

あなたのアプリのstateは、たとえばこれです。

- いま選択されている日付
- 現在時刻
- 展開されている予定のID
- 持ち物のチェック状態

**propsは外から来る値、stateは自分が持っている値**。この区別だけ押さえておけば十分です。

### 3つの関係

```
[state] 選択中の日付 = "2026-09-19"
   │
   │ 変わると再描画
   ▼
[コンポーネント] Timeline
   │
   │ props として予定を渡す
   ▼
[コンポーネント] TimelineItem × 5
```

Claude Code が「この値をstateで持ちますか、propsで渡しますか」と聞いてきたとき、
この図が頭にあれば答えられます。

# 第4章 TypeScriptは何をしてくれるのか

## 型は契約書

JavaScriptは何でも入れられます。
`start` に `"09:30"` を入れても `930` を入れても `null` を入れても、書いた時点では怒られません。
壊れるのは実行してからです。しかも壊れた場所と原因の場所が離れていることが多い。

TypeScriptは、先に「この箱には何が入るか」を宣言させます。

```typescript
type TripItem = {
  id: string;
  start?: string;      // ? は「無くてもいい」の意味
  type: "flight" | "move" | "stay" | "eat" | "play" | "free" | "task";
  title: string;
  place?: string;
  map?: string;
  note?: string;
  booking?: {
    label: string;
    code: string;
    url: string;
  };
};
```

これを書いておくと、`type` に `"dinner"` と書いた瞬間にエディタが赤線を引きます。
実行する前に間違いが分かる。これがTypeScriptの価値です。

## なぜ型定義を最初に作らせるのか

最初のプロンプトで `src/types/trip.ts` を最初に作らせたのには理由があります。

型はJSONとコードのあいだの契約書です。
先に契約書があると、Claude Code はそれに従ってコードを書きます。
JSONの構造を後から変えたときも、影響が出る場所を全部教えてくれます。

契約書を後から書くと、既に書かれたコードに合わせて契約書を歪めることになります。
順番が逆です。

# 第5章 プロジェクトの中身

## ファイルの地図

```
futari/
├─ package.json        このプロジェクトの設定書
├─ node_modules/       ダウンロードしてきた部品の置き場（触らない）
├─ public/             そのまま公開されるファイル（画像、アイコン）
├─ src/                自分が書くコードは全部ここ
│  ├─ main.tsx         最初に読まれるファイル
│  ├─ App.tsx          アプリ全体の入れ物
│  ├─ components/      画面の部品
│  ├─ pages/           画面そのもの
│  ├─ data/            旅程のJSON
│  └─ types/           型定義
├─ functions/          サーバー側のコード（第7章）
└─ index.html          最初に読まれるHTML
```

**自分が触るのは `src/` の中だけ**です。
`node_modules` は数万ファイル入っていますが、一度も開く必要はありません。

## package.json

このプロジェクトが何を使っているかを書いた設定書です。

```json
{
  "dependencies": {
    "react": "^19.0.0",
    "react-router-dom": "^7.0.0"
  },
  "scripts": {
    "dev": "vite",
    "build": "vite build"
  }
}
```

`dependencies` は使っているプラグインの一覧、と考えて構いません。
`npm install` を実行すると、この一覧を見て `node_modules` に実物をダウンロードしてきます。

だから `node_modules` はGitに含めません。package.json があれば復元できるからです。
プロジェクトファイルにサンプル音源を全部埋め込まず、参照だけ持っておくのと同じ発想です。

## npm run dev と npm run build

**`npm run dev`** 開発用に起動します。
`http://localhost:5173` のようなアドレスが表示され、そこを開くとアプリが見えます。
コードを保存すると、ブラウザが即座に更新されます。

DAWで言えばリアルタイム再生です。触りながら確認する状態。

**`npm run build`** 公開用に書き出します。
コードをまとめて圧縮し、`dist/` というフォルダに出力します。これをサーバーに置くと公開されます。

これがバウンスです。仕上げて書き出す。

**localhost はあなたのPCの中だけ**です。彼女には見えません。
彼女に見せるには、buildして公開する必要があります。第8章の話です。

# 第6章 データをどこに置くか

**この章がこの本の核です。**
「彼女とデータを共有する」というあなたの要件が、技術的に何を意味するのかがここで分かります。

## 置き場所は3つある

### 1. コードの中（JSONファイル）

`src/data/trips/minamikyushu-2026.json` のように、リポジトリの中に置く方法です。

- 誰から見えるか → アプリを開いた全員
- 誰が変更できるか → リポジトリを触れる人だけ（つまりあなただけ）
- いつ消えるか → 消えない
- 変更の反映 → ファイルを編集してデプロイし直す必要がある

**確定していて、めったに変わらないデータ向き**です。
飛行機の時刻、予約番号、宿の住所。これらは彼女がアプリから書き換える必要がありません。

### 2. ブラウザの中（localStorage）

ブラウザが端末に持っている小さな保管庫です。

- 誰から見えるか → **その端末のその人だけ**
- 誰が変更できるか → その端末の人
- いつ消えるか → ブラウザのデータを消すまで残る
- 変更の反映 → 即座

ここが重要です。**localStorage は端末を越えません。**
あなたのiPhoneのlocalStorageに書いたものは、彼女のiPhoneからは絶対に見えません。同じURLを開いていてもです。

だから持ち物のチェック状態はここでいい。あなたが自分の荷物にチェックを入れたことを、彼女の画面に反映する必要はありません。

そして**メモの共有には使えない**。これが、次のサーバーが必要になる理由です。

### 3. サーバーの中（データベース）

インターネットのどこかにあるコンピュータの中です。

- 誰から見えるか → アクセス権があれば誰でも、どの端末からでも
- 誰が変更できるか → アクセス権がある人
- いつ消えるか → 消すまで残る
- 変更の反映 → 即座

**2人で同じものを見て、両方が書き換えるデータ**は、ここに置くしかありません。

## なぜ共有にはサーバーが必要なのか

これは技術的な制約ではなく、物理的な話です。

彼女のiPhoneとあなたのiPhoneは、直接つながっていません。
彼女がメモを書いたとき、そのデータがあなたの端末に届くには、**どこかに一度置かれて、あなたがそれを取りに行く**必要があります。

その「どこか」がサーバーです。
郵便局のようなもので、彼女が投函し、あなたが受け取る。直接手渡しはできません。

だから「2人で共有したい」と言った瞬間に、サーバーが確定します。避けようがありません。

## あなたのアプリの割り当て

| データ | 置き場所 | 理由 |
|---|---|---|
| 旅程（日付・時刻・予約番号） | JSON | 確定情報。あなたが作り、彼女は見るだけ |
| 手荷物の規定 | JSON | 変わらない |
| 持ち物のチェック | localStorage | 端末ごとで問題ない。共有不要 |
| メモ・思いつき | **D1（サーバー）** | 2人が書いて2人が読む |
| 候補と投票 | **D1（サーバー）** | 同上 |

この表を持っていれば、Claude Code に「これはどこに置きますか」と聞かれても即答できます。
逆に、Claude Code が持ち物のチェックをD1に入れようとしたら、それは過剰だと判断できます。

## なぜ全部サーバーに置かないのか

置いてもいいのですが、こうなります。

電波がないと旅程が見えません。旅行先で一番見たいときに見えない。
サーバーが落ちたらしおりが開けません。
JSONなら1ファイル編集して終わりの作業に、管理画面が必要になります。

**変わらないものはコードに置き、変わるものだけサーバーに置く。**
これは手抜きではなく、堅牢さのための設計です。

# 第7章 サーバーとは何か

## リクエストとレスポンス

サーバーとのやり取りは、注文と受け取りです。

```
アプリ          「9月18日以降のメモを全部ください」   →   サーバー
アプリ   ←   「はい、3件あります。中身はこれです」        サーバー
```

行きが**リクエスト**、帰りが**レスポンス**。
それだけです。会話ではなく、1回の注文に1回の返事で完結します。

## APIとは

**決められた住所に、決められた形で頼むと、決められた形で返ってくる窓口**のことです。

```
POST /api/posts
本文: { "body": "桜島みたい", "author": "her", "category": "trip:minamikyushu-2026" }
```

この住所とこの形式で送れば、メモが1件保存される。
それが決まっていて、守られている。それがAPIです。

役所の窓口に近い。どの窓口に、どの用紙で出すかが決まっていて、書式が違えば受理されません。

## 4つの動詞

リクエストには種類があります。実質4つ覚えれば足ります。

| 動詞 | 意味 | あなたのアプリでの例 |
|---|---|---|
| GET | 取ってくる | メモ一覧を読む |
| POST | 新しく作る | メモを1件書く |
| PATCH | 一部を書き換える | メモを編集する、投票する |
| DELETE | 消す | メモを削除する |

「メモを編集したい」と言うとき、それは PATCH の話をしています。
この言葉を知っているだけで、Claude Code との会話が一段速くなります。

## なぜアプリから直接データベースを触らないのか

こういう構成にしたくなるかもしれません。

```
アプリ  →  データベース
```

これができない理由は、**鍵の置き場所**です。

データベースを触るには鍵（パスワードのようなもの）が必要です。
アプリはブラウザで動いていて、ブラウザで動くコードは**誰でも中身を読めます**。
URLを知っている人なら、開発者ツールを開けばコードが全部見えます。

そこに鍵を書いておくと、鍵が公開されるのと同じです。

だからこうします。

```
アプリ  →  受付窓口（サーバー）  →  データベース
                 ↑
            鍵はここに置く
```

受付窓口はサーバー側で動くので、中身は誰にも見えません。
鍵をそこに置いておけば安全です。

**アプリは窓口に頼み、窓口がデータベースを触る。** この2段構えが基本形です。

## Cloudflare Pages Functions

その受付窓口を作る仕組みです。

`functions/` フォルダに置いたファイルが、そのまま窓口になります。

```
functions/api/posts/index.ts   →  /api/posts という住所の窓口
functions/api/posts/[id].ts    →  /api/posts/xxx という住所の窓口
```

**ファイルを置いた場所が、そのまま住所になる**。これが分かれば十分です。
サーバーを買ったり、起動しっぱなしにしたりする必要はありません。リクエストが来たときだけ動きます。

## D1

Cloudflareが提供するデータベースです。中身はSQLiteという定番のもの。

データベースは表計算ソフトだと思ってください。

**テーブル** = シート1枚
**列** = 縦の項目（id、本文、書いた人、書いた日時）
**行** = データ1件

あなたの `posts` テーブルはこうなっています。

| id | category | body | author | status | created_at |
|---|---|---|---|---|---|
| abc | trip:minamikyushu-2026 | 桜島みたい | her | open | 2026-09-01... |
| def | idea:minamikyushu-2026 | 城山展望台 | me | open | 2026-09-01... |

## SQLは4つ覚えれば足りる

データベースに話しかける言葉がSQLです。書くのはClaude Codeですが、読めた方がいい。

```sql
-- 読む
SELECT * FROM posts WHERE category = 'trip:minamikyushu-2026';

-- 書く
INSERT INTO posts (id, body, author) VALUES ('abc', '桜島みたい', 'her');

-- 直す
UPDATE posts SET body = '城山から桜島' WHERE id = 'abc';

-- 消す
DELETE FROM posts WHERE id = 'abc';
```

`SELECT` `INSERT` `UPDATE` `DELETE` の4つ。
そして `WHERE` が「どれに対して」を指定する条件です。

ちなみに仕様書では `DELETE` を使わず、`deleted_at` に時刻を入れて「消したことにする」方式にしています。
これを論理削除と呼びます。誤って消しても戻せるからです。

## 環境変数

パスフレーズのような秘密の値を、コードに直接書かない仕組みです。

```typescript
// これはダメ。コードを見た人に全部バレる
if (password === "futari2026") { ... }

// これが正しい。値はCloudflareの管理画面に登録しておく
if (password === env.APP_PASSPHRASE) { ... }
```

コードには「金庫の中のあの値」とだけ書き、実際の値は別の場所に保管する。
Gitにも上がらないので、公開リポジトリにしても漏れません。

## 認証について

あなたのアプリの認証はこうなっています。

1. 初回にパスフレーズを入力する
2. 窓口が環境変数と照合する
3. 合っていれば端末に保存し、次から自動で送る

2人しか使わないので、これで十分です。
本格的なログインの仕組みは、大勢が使い、人によって見えるものが違う場合に必要になります。あなたのアプリはどちらでもありません。

「シンプルすぎないか」と不安になるかもしれませんが、**要件に対して過剰な仕組みを入れることは、それ自体がリスク**です。作るものが増えれば壊れる場所も増えます。

# 第8章 gitとデプロイ

## gitはセーブポイント

コードの状態を保存し、いつでも戻れるようにする仕組みです。

```bash
git add .                      # 保存する変更を選ぶ
git commit -m "日程タブを追加"  # セーブポイントを作る
git push                       # GitHubに送る
```

**commit** がセーブ、**push** がクラウドへのアップロードです。

これが効いてくるのは、Claude Code に作業させるときです。
commitしてから作業させれば、結果が気に入らなければ元に戻せます。

```bash
git checkout .   # 最後のcommit以降の変更を全部捨てる
```

**大きな変更を頼む前には必ずcommitする。** これは強く勧めます。
Claude Code が意図と違う方向に10ファイル書き換えたとき、これがあるかないかで消耗が全く違います。

## デプロイ

書き出したものをサーバーに置いて、公開状態にすることです。

Cloudflare Pages とGitHubを繋いでおくと、これが自動になります。

```
git push  →  Cloudflareが検知  →  自動でbuild  →  公開URLが更新される
```

一度設定すれば、以降は push するだけです。

## ローカルと本番の違い

| | ローカル | 本番 |
|---|---|---|
| URL | localhost:5173 | 公開URL |
| 誰が見えるか | 自分だけ | URLを知っている人 |
| データベース | ローカルのD1 | 本番のD1 |
| 反映 | 保存で即座 | pushしてから1〜2分 |

**ローカルで動いたから本番でも動く、とは限りません。**
特にサーバー側は設定が別なので、本番で初めて壊れることがあります。

だからメモ機能を作ったら、一度デプロイして実機で試してください。
彼女に見せる前に、自分のiPhoneで開いて投稿できることを確認する。ここを飛ばすと、見せた瞬間に動かないという事故が起きます。

# 第9章 PWA

## ホーム画面に置ける理由

`manifest.json` というファイルが正体です。

```json
{
  "name": "ふたりのしおり",
  "display": "standalone",
  "icons": [{ "src": "/icons/192.png", "sizes": "192x192" }]
}
```

これを置いておくと、ブラウザが「これはアプリとして扱っていいものだ」と判断します。
iPhoneなら共有ボタンから「ホーム画面に追加」を選ぶと、アイコンが並びます。

`"display": "standalone"` が、開いたときにアドレスバーを消す指定です。
これがあるかないかで、ふつうのアプリに見えるかどうかが決まります。

## オフラインで開ける理由

**Service Worker** という仕組みです。

ブラウザとインターネットのあいだに座っている係員だと思ってください。

```
通常:      アプリ  →  インターネット  →  ファイル

SW あり:   アプリ  →  Service Worker  →  手元にあればそれを返す
                            ↓
                      なければインターネットへ
```

一度読んだファイルを手元に取っておいて、次からはそれを返す。
だから電波がなくても開けます。

あなたのアプリでは、旅程JSONと画面のファイルを全部取っておきます。
現地で電波が弱くても、しおりは開ける。これが仕様書で「オフラインで全ページ閲覧できること」と書いた理由です。

## よくある落とし穴

Service Worker は古いファイルを返し続けることがあります。
更新したのにスマホで反映されない、という現象が起きます。

その場合はこうします。

- ホーム画面のアイコンを消して、もう一度追加する
- ブラウザでURLを開いてリロードしてから、ホーム画面に追加し直す

「更新したのに彼女の端末で古いまま」というときは、まずこれを疑ってください。
コードのバグではないことが多いです。

# 第10章 的確なプロンプトの打ち方

**ここがこの本のゴールです。**

## 6つの原則

### 原則1 完成の条件を書く

「何を作るか」ではなく「どうなっていれば完成か」を書きます。

```
❌ 日程タブを作って
```

これだと、Claude Code は無数にある解釈の中から1つを選びます。当たる確率は低い。

```
✅ 日程タブを実装してください。完成条件は以下です。
   - 上部に日付チップが横スクロールで並び、タップで切り替わる
   - 選択日の予定が時系列に縦に並ぶ
   - 時刻は等幅フォントで、本文より一段大きい
   - 現在時刻が選択日の範囲内なら、その位置に横線が引かれる
   - 過ぎた予定は薄く表示される
   - 375px幅で横スクロールが発生しない
```

チェックリストとして書くと、Claude Code は自分で検証できます。
あなたも受け取ったものを判断できます。

### 原則2 やらないことを書く

これを書かないと、範囲が勝手に広がります。

```
✅ 今回のスコープは日程タブだけです。
   以下には触れないでください。
   - D1、Pages Functions、メモ機能
   - PWA設定
   - 他のタブ
```

**スコープを閉じるのは、指示を出す側の仕事**です。
書かなければ、全部作られます。そして直す量が増えます。

### 原則3 止め所を指定する

```
✅ 実装したら npm run dev で起動し、375px幅の
   スクリーンショットを見せてください。そこで止まってください。
```

一度に大量に作らせると、どこで方向がずれたか分からなくなります。
小さく作って見て、次へ進む。この繰り返しが結局いちばん速い。

### 原則4 判断材料を先に渡す

毎回長い説明を書く必要はありません。**CLAUDE.md と仕様書に書いておけばいい。**

```
✅ docs/spec.md を読んでから始めてください。
```

CLAUDE.md はプロジェクトのルート に置いておくと、Claude Code が自動で読みます。
「毎回言っていること」は、そこに書けば言わなくて済みます。

逆に言えば、**同じ指摘を2回したら、それはCLAUDE.mdに書くべき内容**です。

### 原則5 証拠を要求する

```
❌ 動いてる？
✅ 実際に npm run dev で起動して、スクリーンショットを見せてください
✅ そのエラーが消えたことを、実行結果で示してください
```

「動きました」という報告ではなく、動いている証拠を求める。
これは疑っているのではなく、思い込みで進まないための手順です。

### 原則6 2回直らなかったらやり直す

同じ問題を2回指摘して直らないときは、会話が長くなりすぎて混乱している可能性が高い。

`/clear` で会話をリセットし、状況を整理してから頼み直します。
このとき、CLAUDE.md と仕様書に必要な情報が書いてあれば、リセットしても失うものはありません。

粘って往復するより、切って出し直す方が速い。

## プラン モード

コードを書かせる前に、何をするつもりか説明させる機能です。

`Shift+Tab` を押すと、ステータスバーに「plan mode on」と表示されます。
このモードでは、Claude Code はファイルを読んで計画を提示するだけで、承認するまで一切編集しません。

**大きな変更を頼むときは、まずプラン モードで方針を見る。**
違う方向を向いていたら、書かれる前に止められます。書かれた後に直すより圧倒的に安い。

## エラーが出たときの渡し方

```
❌ エラーが出た。直して
```

```
✅ npm run dev したらこのエラーが出ました。
   （エラーメッセージを全文そのまま貼る）
   直前に日程タブのファイルを追加しました。
```

**エラーメッセージは要約せず、全文をそのまま貼る**のがコツです。
一見どうでもよさそうな行に原因が書いてあることが多い。

そして「直前に何をしたか」を添える。原因の8割はそこにあります。

## あなたのアプリでの実例

**悪い例**

```
メモ機能つけて
```

**良い例**

```
docs/spec.md の「タブ3: メモ」を実装します。

今回のスコープ:
- D1のマイグレーション（posts テーブル）
- functions/api/posts/index.ts の GET と POST
- メモタブのUI（一覧表示と、下部の1行入力欄）

今回やらないこと:
- 候補タブと投票機能
- オフライン送信キュー
- 編集と削除

完成条件:
- メモを投稿すると即座に一覧の先頭に出る
- リロードしても消えない
- 投稿者の色ドットが左端に出る
- 一覧が空のとき、仕様書に書いた空状態の文言が出る

まず wrangler での D1 セットアップ手順を提示してください。
そこで一度止まってください。私が実行します。
```

長く見えますが、これを書く3分で、往復10回分が節約できます。

## 迷ったときの型

```
【やること】
【やらないこと】
【完成条件】（箇条書き）
【止め所】
```

この4つを埋めるだけで、プロンプトの質は安定します。

# 第11章 詰まったときに読むところ

## エラーメッセージの読み方

エラーは3つの情報を持っています。

```
TypeError: Cannot read properties of undefined (reading 'items')
    at Timeline (Timeline.tsx:24:18)
```

1. **種類** `TypeError` = 型がおかしい
2. **内容** undefined のものから `items` を読もうとした
3. **場所** Timeline.tsx の24行目

この例の意味は、「あるはずの日付データが無かったのに、その中の予定一覧を読もうとした」です。
たとえば9月23日を選んだのに、JSONにその日が無い、というような状況。

**種類・内容・場所の3つを拾う**。それだけで、何が起きたかの見当がつきます。

## よくある症状

| 症状 | よくある原因 |
|---|---|
| 画面が真っ白 | JavaScriptのエラーで描画が止まった。ブラウザのコンソールを見る |
| 変更が反映されない | dev サーバーが止まっている、またはService Workerが古いものを返している |
| ローカルでは動くが本番で動かない | 環境変数が本番に登録されていない |
| 彼女の端末だけ表示が違う | ブラウザの差、またはキャッシュ |
| データが消えた | localStorageに入れていた。サーバーに移すべきものだった |

## 用語辞典

**リポジトリ** プロジェクトのフォルダ全体。Gitで管理されている単位

**コミット** 変更のセーブポイント

**プッシュ** ローカルの変更をGitHubに送ること

**ビルド** 公開用にコードをまとめて書き出すこと

**デプロイ** 書き出したものをサーバーに置いて公開すること

**バンドル** 大量のファイルを1つにまとめること。Viteがやってくれる

**依存関係（dependencies）** このプロジェクトが使っている外部の部品

**フロントエンド** ブラウザで動く部分。画面

**バックエンド** サーバーで動く部分。窓口とデータベース

**エンドポイント** APIの窓口1つ分の住所。`/api/posts` など

**レスポンス** サーバーからの返事

**ステータスコード** 返事に付く番号。200は成功、401は認証エラー、404は見つからない、500はサーバー側の故障

**マイグレーション** データベースの表の構造を作ったり変えたりすること

**論理削除** 実際には消さず、消したという印を付けること

**環境変数** コードに書かず外に置く設定値。主に秘密のもの

**キャッシュ** 一度取ったものを取っておいて再利用すること

**Service Worker** ブラウザとネットのあいだに座る係員。オフライン対応の正体

**マニフェスト** ホーム画面に置くための設定ファイル

**楽観的更新** サーバーの返事を待たずに、先に画面を更新してしまうやり方。速く感じる

# 付録 あなたの実装順序

仕様書に書いてある順番の意図です。

**1. 型定義とデータ読み込み**
契約書を先に作る。ここが決まると後がぶれない。

**2. 日程タブ**
一番使う画面であり、デザインの手触りがここで決まる。
375px幅で実際にスクロールして、時刻の大きさと余白を確定させる。

**3. 今日タブ / 持ち物タブ / 情報タブ**
日程タブで決めた見た目を横展開する。ここは速い。

**4. PWA設定**
ホーム画面に置けるようにする。実機で確認する。

**5. D1とPages Functions**
サーバー側。ここで初めてバックエンドに触る。
UIが固まってから着手するのは、手戻りを減らすため。

**6. メモタブと候補タブ**
書き込み機能。彼女に見せられる状態になる。

**この順番を守る理由は、後戻りが最小になるからです。**
先にサーバーを作ると、UIが変わるたびにAPIも直すことになります。
